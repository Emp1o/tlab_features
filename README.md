# Признаки для ранжирования RetailRocket

## Коротко

Все этапы задания выполнены: бустинг на ручных признаках, автогенерация и автоматический отбор признаков, сравнение на одном разбиении по времени. Автоотбор сократил число признаков со 152 до 21, и **значимой разницы с бустингом на ручных признаках не обнаружено** ни на одной выборке: на test разница manual − A_new составляет +0.003 NDCG@3 (95% ДИ от −0.019 до +0.025). Предрегистрированная гипотеза «A_new лучше popularity на test» не подтвердилась: +0.013 (95% ДИ от −0.009 до +0.036).

|---|---:|---|

## Задача

Нужно ранжировать товары для пользователя. Модель — бинарный LightGBM: метка 1, если в этот день была покупка (`transaction`). Корзина без покупки — 0. Основная метрика — NDCG@3. Рядом считаются NDCG@5, MRR, AUC, Recall@3, Recall@5 и LogLoss.

Группа ранжирования — пара (пользователь, день). В среднее NDCG, MRR и Recall входят только группы, где товаров не меньше двух и есть хотя бы одна покупка.

## Почему RetailRocket

RetailRocket — открытый датасет с реальными событиями интернет-магазина: просмотр, добавление в корзину и покупка, у каждого события есть отметка времени. Это соответствует условию задания: каждая строка — (пользователь, товар, время, тип события).

- **Метка без ручной разметки.** Метку покупки можно взять прямо из событий `transaction`.
- **Честное разбиение по времени.** Отметки времени позволяют разделить данные на обучение, валидацию и тест строго по времени.
- **Свойства товаров.** История наличия и категории товаров, которая есть в датасете, позволила построить признаки категорий и наличия и проверить их полезность.

**Слабые стороны, выявленные в процессе работы:** мало покупок: лог большой (2,76 млн событий), но покупок 0,81%, и в test всего 584 группы с покупкой; большое число клиентов, купивших только один или два товара (10 834 из 11 719 покупателей во всём логе); мало разных действий и изменений в выбранном промежутке (медиана 1 событие на пользователя, три типа событий). Это повлияло на итоговые результаты и на неопределённость при сравнении моделей. Числа лога — в [`report/dataset_sparsity.csv`](report/dataset_sparsity.csv), их пишет `src/dataset_sparsity.py`.

## Кандидаты

Модель переранжирует товары, с которыми пользователь взаимодействовал в день D. Покупка в день D сама является взаимодействием, поэтому купленный товар уже есть в списке. Recall множества кандидатов равен 1 по построению: это не поиск кандидатов из всего каталога.

Метрики ранжирования считаются только по группам с не меньше чем двумя товарами и хотя бы одной покупкой.

Признаки смотрят только события строго до начала дня D. Категория строки и наличие — последний снимок с timestamp строго раньше 03:00 этого дня. Категория прошлой покупки берётся на момент той покупки. Неизвестная категория или снимок — пустое значение, не ноль.

## Генератор признаков

Сетка основного файла зафиксирована: окна 1, 7, 14 и 30 дней, 152 признака. Отдельный предрегистрированный поиск сетки {1, 3, 5, 7, 10, 14, 21, 30} описан ниже. Он не заменил A_new и не переписывает файл на 152 признака.

События: `view`, `addtocart`, `transaction`.
Окна: 1, 7, 14, 30 дней.
Сущности: пользователь, товар, пара пользователь–товар, категория, пользователь–категория.
Сводки: число, доля, давность, тренд, число разных товаров.

У давности окна нет. Тренд — отношение числа за 7 дней к числу за 30. Число разных товаров считается только у пользователя и у категории.

Сверх сетки, шаг 4: две личные покупки в категории товара, две сводки по категории (число за 30 дней и доля повторных), давность личной покупки в категории, наличие товара as-of и число переключений 0↔1. Если покупок в категории меньше пяти, доля повторных сглаживается: (повторные + 1) / (покупки + 2). Если покупок не было — пусто.

В файле кандидатов 152 признака: 145 до шага 4 и 7 признаков шага 4.

Отборщик v2, только на train: сила = |group AUC − 0.5|, порог = средняя сила, дубли при |Спирмен| > 0.9. Итоговый набор — A_new, 21 признак. Решение по предрегистрированному правилу второго периода. Этот аудит набор не менял.

Число деревьев A_new — 80, медиана best_iteration на val1 (77, 80, 91, 84, 78). A_new+7 тоже учится на 80, хотя его собственная медиана на val1 равна 72. У manual в этом аудите 89 деревьев, у C — 78. Сиды 42–46, в метрику идёт среднее вероятностей, столбцы по алфавиту. Ничья равных предсказаний у моделей — seed 42, у бейзлайнов — seed 0. Бутстреп парный, 1 000 повторов групп, seed 42, квантили 2.5 и 97.5. Внутри одного периода индексы одни и те же.

## Ограничения

Один период test, 14 дней, один датасет RetailRocket. Бутстреп по группам (пользователь, день), не по пользователям. Отбор A_new видел данные val2, поэтому val2 не полностью независим. Сводки test при старой метке cart|purchase были в коммите e0718b8: `report/notes.md` записал 205 488 строк, долю положительных 2,9% и 1 964 ранжирующие группы; `src/prepare.py` в том коммите печатал число строк, долю положительных и число групп по всем сплитам, включая test. Это не нынешние числа метки «только покупка». Метрика ранжирования считается только по группам с хотя бы одной покупкой. Список кандидатов — товары, с которыми пользователь уже взаимодействовал в день D, поэтому recall кандидатов равен 1 по построению. Окна основного файла 1, 7, 14 и 30 дней. Поиск более широкой сетки — отдельный прогон: тренд по-прежнему одна пара 7/30, и по правилу val2 A_new не заменён. Post-hoc test описательный и не меняет предрегистрированный вывод основного test.

- Признаки строятся только по прошлому, разбиение — по времени.

- Независимая проверка показала, что отбор видел val2. Повторный отбор только на train2 дал почти тот же набор (23 признака, совпадение 91%) и незначимую разницу (+0.002). Test в отборе не участвовал, поэтому оценка на нём не завышена подбором.

### 4. Что не сработало
Было несколько гипотез о новых признаках, не все подтвердились на данных:
- Автоподбор окон (W_auto): эффекта не обнаружено, −0.006 к A_new на test. На вопрос «почему именно 7 дней» ответ здесь такой: улучшения качества от перебора окон не обнаружено.
- Признаки по категориям и по давности покупки не прошли отбор.
- Признак наличия товара прошёл отбор, но эффекта не обнаружено.

### 6. Ограничения
Один датасет (RetailRocket), test на 14 дней и 584 группы, генерация кандидатов дороже ручных признаков, отбор видел val2. Ограничения самого датасета — в разделе «Почему RetailRocket».

### 7. Почему val и test расходятся
На val1 разница A_new − popularity при 80 деревьях была +0.0175, на test +0.013. Выделяется в основном val2: там разница +0.044. [Cawley & Talbot (2010), JMLR](https://jmlr.org/papers/v11/cawley10a.html) поддерживают общий тезис: отбор по валидации даёт оптимистичную оценку, поэтому нужен нетронутый тест. Эффект отбора по валидации и различие периодов — возможные объяснения, они не проверены.

### Итог
Автоотбор даёт в 7 раз более компактный набор признаков (21 вместо 152) без обнаруженной потери качества относительно бустинга на ручных признаках: на test разница от −0.019 до +0.025 NDCG@3. Доказать равенство в пределах ±0.01 NDCG@3 на этих данных нельзя: тест слишком мал: чтобы интервал хотя бы сузился до ±0.01, нужно как минимум примерно в 5 раз больше групп с покупкой (около 2800 вместо 584), а для надёжной проверки эквивалентности (TOST, мощность 80%) — порядка в 10 раз больше (около 6000). Следующий шаг — проверка на большем объёме данных и на втором датасете (KION или Yambda) с заранее заданным порогом эквивалентности ±0.01.
